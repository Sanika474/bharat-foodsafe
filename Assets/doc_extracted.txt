1. Executive Summary
Bharat FoodSafe is a mobile-first operational assurance platform for restaurants, cafés, cloud kitchens, canteens and caterers. It converts applicable food-safety requirements and restaurant SOPs into recurring tasks, captures execution evidence, evaluates recorded conditions with deterministic rules, separately analyzes record-integrity anomalies, manages incidents and corrective actions, and preserves an auditable history.
The platform is not an FSSAI licensing portal, official inspection system, complaint portal, laboratory system, foodborne-illness diagnostic system, or replacement for physical inspection or laboratory testing. It is an operational layer between documented requirements and daily execution.
Verified rule source / restaurant SOP        ↓Task template + immutable version        ↓Scheduled task instance        ↓Staff execution        ↓Value + evidence        ↓Deterministic safety evaluation        ↓Record-integrity analysis        ↓Normal / review / deviation / critical        ↓Incident + corrective action when configured        ↓Re-check → Manager verification        ↓Audit history + reporting
1.1 Final architecture decision
One modular-monolith backend; no microservice split for MVP.
PostgreSQL is the system of record.
Evidence binaries live in object storage; PostgreSQL stores metadata, hashes and lifecycle state.
Safety Rules Engine and Record-Integrity Anomaly Engine are independent.
ML never invents regulatory thresholds and never proves fraud.
Tenant isolation is enforced server-side through TenantContext and scoped repositories/services.
Workflow state changes use explicit command endpoints; generic status PATCH is prohibited.
Retryable business writes use persistent idempotency.
Auditable mutations write audit events in the same transaction as the mutation.
Critical notifications use a transactional outbox; provider calls are asynchronous.
Regulatory rule activation requires a verified RuleSource.

4.1 Non-functional requirements
Security: credential hashes only, server-side authorization, tenant isolation, secret management.
Auditability: actor, tenant, entity, action, request ID, timestamp and relevant before/after values.
Reliability: transactional critical workflows, idempotent writes, recoverable outbox.
Performance: paginated lists, indexed queues, aggregate dashboards, bounded ML inference.
Accessibility: semantic labels, keyboard access, focus states, contrast and readable validation.
Responsive UX: staff mobile-first; manager/admin desktop-first responsive.
Observability: structured logs, request IDs, health/readiness, error and job metrics.
Privacy: no employee/raw evidence/internal notes in public APIs.
Regulatory freshness: source/version/effective-date records; no silent threshold mutation.

6.1 Canonical request lifecycle
HTTP Request→ Request ID→ CORS/security middleware→ Authenticate access token→ Validate user/session status→ Resolve permission→ Resolve TenantContext→ Validate Pydantic DTO→ Idempotency check (retryable writes)→ Begin service transaction→ Domain service→ Repository / engine calls→ Audit event(s)→ Outbox event(s) if required→ Commit→ Response DTO
Routers contain HTTP concerns only.
Services own business workflows and transaction boundaries.
Repositories perform database access only.
Engines are deterministic/pure where practical.
ORM models never leak directly through API responses.
Cross-domain calls use service interfaces, not direct SQL from another module.
7. Database Architecture
PostgreSQL is the system of record. UUID primary keys and UTC TIMESTAMPTZ timestamps are used throughout. JSONB is reserved for versioned/configurable structures, rule conditions/actions, model explanations/features, and extracted verification fields.

9. Safety Rules Engine
The Safety Rules Engine answers: “Does the recorded condition violate a configured rule?” It is deterministic, versioned, source-linked and independent from anomaly scoring.

Restaurant-specific rule where authorized

9.2 Output
{  "status": "NORMAL | DEVIATION | CRITICAL",  "rule_id": "uuid",  "severity": "LOW | MEDIUM | HIGH | CRITICAL",  "reason": "Configured condition was not satisfied",  "required_action": "Configured SOP / create incident"}
9.3 Rule versioning and activation
Each safety_rules row represents one immutable rule version.
rule_code identifies the logical rule; version_number identifies the version.
supersedes_rule_id links a new version to the prior version.
PATCH on a used rule never mutates the historical row; it creates a new version.
No rule may activate unless its RuleSource.review_status is VERIFIED.
Regulatory values are not hard-coded in Python source.
Historical entry evaluations reference the exact rule and source version used.
Platform rules may apply across restaurants; restaurant-specific rules may add stricter conditions but may not silently weaken a platform CRITICAL rule.
Conflicting rules resolve by severity. Equal-severity conflicts return REVIEW and are recorded for admin review.
9.4 Rule binding validation
CATEGORY binding target_id must exist in task_categories.
TEMPLATE binding target_id must exist in task_templates.
A rule without a binding may remain DRAFT but cannot affect tasks.
Template-specific binding changes applicability only; it never bypasses source verification.

12. Idempotency Contract
Retryable business mutations require Authorization plus Idempotency-Key. Authentication endpoints, health endpoints and semantically idempotent DELETE operations are documented exceptions.
First request:PROCESSING row is created under UNIQUE(user_id,key)→ business transaction executes→ COMPLETED row stores status + responseConcurrent same request:→ detects PROCESSING→ waits/retries/replays; no duplicate business effectSame key + different canonical request:→ 409 IDEMPOTENCY_KEY_REUSE
request_hash covers HTTP method, path, authenticated user and canonical request body.
Idempotency is checked before business side effects.
The final response is stored for replay.
Failed attempts are represented as FAILED when no successful business result exists.
Keys expire and are cleaned by a scheduled job.
No duplicate entry, incident, audit or notification side effects are allowed.
13. Audit Integrity and Hash Chain
Auditable mutations and denied security actions produce append-only audit events in the same database transaction as the relevant mutation whenever applicable.
13.1 Canonical audit event
idactor_idrestaurant_idchain_scopeentity_typeentity_idactionold_valuenew_valuetimestamprequest_idprevious_hashrecord_hash
record_hash = SHA-256(UTF-8 canonical JSON of the event including previous_hash)
13.2 Concurrency control
Determine chain_scope. Use a stable restaurant scope for tenant events and PLATFORM for platform-only security events.
Start the service transaction.
Acquire a PostgreSQL transaction-level advisory lock derived from chain_scope using pg_advisory_xact_lock.
Read the latest audit event for that chain_scope.
Set previous_hash to the latest record_hash, or NULL for the first event.
Canonicalize the event deterministically and compute SHA-256.
Insert the audit row.
Commit together with the business mutation/outbox row.
No normal application UPDATE or DELETE endpoint exists for audit_log.
Sensitive fields are redacted before persistence.
Large payloads are represented as field-level changes rather than binary content.
An audit verification utility can recompute the chain and report the first broken link.

21. Canonical End-to-End Data Flows
21.1 Staff entry flow
GET /tasks/today→ open task→ POST /tasks/{id}/start→ enter value/checklist→ POST /uploads/presign→ upload to object storage→ POST /uploads/{id}/confirm→ POST /tasks/{id}/entries→ verify assignment/state/evidence/value/equipment→ deterministic Safety Rules Engine→ entry_safety_evaluations→ Record-Integrity Engine→ trust/result calculation→ incident/CAPA if needed→ audit + outbox→ COMMIT→ response
21.2 Critical deviation flow
Entry→ Safety Rules = CRITICAL→ entry.safety_status = CRITICAL→ Incident OPEN→ CAPA OPEN→ manager notification via outbox→ corrective action→ recheck→ verification→ incident CLOSED→ audit timeline
21.3 Suspicious record flow
Entry→ Safety Rules = NORMAL→ Anomaly = REVIEW→ record is NOT declared unsafe→ manager reviews→ accept / request recheck / escalate→ decision audited
21.4 Public profile flow
Public request→ is_public check→ allow-list aggregate query→ exclude employees/raw evidence/internal notes→ include freshness + disclaimer→ return PublicProfileDTO
21.5 Verification flow
Manager submits business metadata→ upload validation→ verification document association→ optional OCR adapter→ consistency checks→ confidence→ VERIFIED / NEEDS_MANUAL_REVIEW / MORE_EVIDENCE / REJECTED→ admin decision where required→ audit
22. Supplier, Product and Receiving Scope
Supplier  ↓Product  ↓Batch received  ↓Quantity + batch number + expiry + received_at  ↓Optional receiving evidence  ↓PENDING → ACCEPTED / REJECTED / HOLD
Included: supplier master, product master, batch traceability, expiry tracking, basic receiving status and optional receiving evidence.
Excluded: purchase orders, invoice OCR, full inventory management, multi-tier supply chain.
23. Public Profile and Official Records
Public profile is an operational-transparency artifact.
Only explicitly approved aggregate data is published.
Raw employee records, raw evidence, internal notes and private storage keys are never public.
Public profile shows freshness timestamp and a clear non-certification disclaimer.
official_records may be displayed only when independently verified and never imply that Bharat FoodSafe issued the official status.
